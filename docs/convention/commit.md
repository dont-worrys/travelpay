# 커밋 메시지 규칙

변경 이력에서 목적과 영향 범위를 알아볼 수 있도록 Conventional Commits 형식을 사용합니다. 설명은 한국어로 작성할 수 있습니다.

## 형식

```text
type: 변경 내용을 한 줄로 요약

필요하면 변경 이유와 영향을 본문에 작성

Refs #이슈번호
```

- type은 소문자로 작성합니다.
- 괄호로 스코프를 붙이지 않고 모든 커밋에 `type: 설명` 형식을 사용합니다.
- 요약은 변경 결과를 구체적으로 적고 끝의 마침표는 생략합니다. 한 줄에 읽을 수 있는 길이를 권장합니다.
- 하나의 커밋은 함께 적용하고 되돌릴 수 있는 변경 단위로 구성합니다.
- 이슈 번호를 매 커밋 제목에 반복할 필요는 없습니다. 필요하면 본문에 `Refs #12`처럼 연결합니다.

## type

| type | 사용 기준 |
|---|---|
| feat | 새로운 기능이나 외부 동작 추가 |
| fix | 잘못된 동작 수정 |
| refactor | 외부 동작을 유지하는 내부 구조 개선 |
| docs | 문서 변경 |
| test | 테스트 추가·수정 |
| build | Gradle·의존성·빌드 방식 변경 |
| ci | CI 자동화 설정 변경 |
| chore | 그 밖의 설정·도구·코드 정리 |

## 예시

```text
feat: 일반 회원가입 API 추가
fix: 같은 멱등 키의 중복 금액 처리 방지
build: 서비스 공통 의존성 버전 관리
docs: 로컬 실행 가이드 작성
chore: 초기 개발 환경 구성
```

PR을 Squash merge할 때는 최종 커밋으로 남을 PR 제목도 같은 형식으로 작성합니다. 이 문서 자체가 자동 버전 배포나 커밋 검증 도구를 설정하지는 않습니다.

근거: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
