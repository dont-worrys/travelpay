# CI·CD 가이드

GitHub Actions로 PR을 검사하고(CI), main에 반영된 커밋을 운영에 배포합니다(CD). 인프라 담당자의 AWS·GitHub 설정 절차는 [AWS Terraform 실행 가이드](aws-terraform.md#자동-배포cd-연결)에 있습니다.

## CI(PR 검사)

PR이 `dev`·`main`을 대상으로 열리거나 갱신될 때와 `dev`에 반영될 때 돕니다. 같은 PR에 새 커밋이 오면 이전 실행을 멈춥니다. `main`에 반영된 커밋은 CD가 배포하기 전에 같은 CI(`ci.yml`)를 불러 검사합니다.

| 워크플로 | 작업 | 검사 내용 |
|---|---|---|
| `ci.yml` | Gradle build | Docker 사용 가능 여부를 확인한 뒤 `./gradlew build --parallel --build-cache`로 모든 서비스의 컴파일·테스트. 서비스 통합 테스트는 Testcontainers로 Docker를 씁니다 |
| `ci.yml` | Terraform | `infra/aws` 형식(`fmt -check`), 본 root와 State bootstrap root의 `validate`·`test`. State·AWS 자격 증명 없이 모의 provider로 검사합니다 |
| `ci.yml` | Python 3.9 | 인프라 스크립트 테스트. 3.9는 Data·앱 호스트(AL2023)의 `python3` 버전이며, DB 초기화 SQL을 실제 PostgreSQL로 검사합니다 |
| `ci.yml` | Python 3.15 | 같은 테스트를 인프라 담당자 PC 도구(비밀값 준비·이미지 게시)용 최신 버전으로 |
| `ci-container.yml` | Image and monitoring | 실행 이미지를 실제로 빌드해 실행 사용자·권한·시작 스크립트를 확인하고, 운영 Alloy·Loki 설정으로 로그 레이블을 확인합니다. 오래 걸리므로 Dockerfile·시작 스크립트·`.dockerignore`·Gradle 빌드 설정·모니터링 설정이 바뀐 경우에만 돕니다 |

실패하면 Actions 화면의 해당 작업 로그를 봅니다. Gradle 테스트가 실패하면 테스트 보고서(`gradle-test-reports`)를 7일 동안 내려받을 수 있습니다. 로컬에서 같은 검사를 돌리는 명령은 각 작업의 `run` 줄과 같습니다. Gradle은 로컬에서 `./gradlew build`로 충분하고, `--build-cache`를 붙일 때는 Docker를 켠 상태에서 돌립니다(아래 "실행 시간").

### 실행 시간

CI 시간은 대부분 Gradle 작업입니다(2026-11-13 이전 최근 10회 중간값 575초, 그중 `./gradlew build` 단계가 559초). 두 옵션으로 줄이며, CI 명령에만 붙여 로컬 빌드에는 영향이 없습니다.

- **병렬 실행(`--parallel`):** 서로 다른 서비스의 작업을 동시에 돌립니다. 같은 커밋으로 3번 재니 Gradle 작업이 349·464·409초(중간값 409초)였습니다. 같은 코드를 병렬 없이 돌린 2번(473·572초)과 최근 10번(중간값 575초)보다 모두 짧아, 중간값 기준 약 20~30% 줄었습니다. 모든 서비스의 테스트를 실제로 동시에 돌린 4번(병렬만 3번, 캐시가 빈 실행 1번)이 모두 통과했습니다.
- **빌드 캐시(`--build-cache`):** 입력(소스·의존성·설정)이 같은 작업은 다시 실행하지 않고 저장된 결과를 씁니다. `dev` 실행이 결과를 캐시에 저장하고 PR과 main 실행은 읽기만 하므로, 바뀌지 않은 서비스의 컴파일·테스트는 건너뜁니다. `common/`은 Eureka를 뺀 7개 서비스가 쓰므로, 바뀌면 거의 모든 서비스의 테스트가 다시 돕니다. PR 측정에서 저장된 빌드 캐시 항목은 11.5MiB였습니다.

두 옵션을 함께 켜고 잰 Gradle 작업 시간입니다(2026-11-13, PR #309). 측정하는 동안에만 PR이 자기 캐시를 저장하게 해서 `dev` 캐시를 대신했습니다.

| 상황 | Gradle 작업 |
|---|---|
| 캐시가 비어 있을 때(이 설정이 `dev`에 들어간 뒤 첫 실행, 캐시를 지운 뒤, Gradle·의존성 버전을 바꾼 직후) | 478초 |
| 문서만 바뀐 PR(컴파일·테스트를 모두 캐시에서 복원) | 52초 |
| 서비스 하나(user-service)의 테스트 설정만 바뀐 PR(그 서비스 테스트만 다시 실행, 컴파일은 복원) | 195초 |

빌드 캐시는 테스트 결과도 입력이 바뀌기 전까지 다시 씁니다. 병렬 실행에서는 여러 서비스의 테스트가 CPU 4개를 나눠 씁니다. 그래서 다음을 지킵니다.

- 테스트 결과가 Gradle이 입력으로 보지 않는 것(현재 시각, 외부 서비스, 환경 변수, JDK 패치 버전)에 따라 달라지지 않게 씁니다. 그런 테스트는 잘못된 결과가 캐시에 남을 수 있습니다(Gradle 문서).
- Testcontainers 이미지는 `postgres:18.6-bookworm`처럼 버전으로 고정합니다. `latest` 같은 태그는 이미지가 바뀌어도 캐시된 결과가 그대로 쓰입니다. 공식 이미지는 기반 OS 갱신 때 다시 빌드되므로(Docker 공식 이미지 FAQ), 완전히 고정하려면 digest를 씁니다.
- Docker가 없으면 `@Testcontainers(disabledWithoutDocker = true)`인 통합 테스트(46개 클래스)가 건너뛰어진 채 통과로 끝나고, 그 결과도 캐시에 남습니다. CI는 캐시 복원 전에 `docker info`로 Docker 사용 가능 여부를 확인하고, 사용할 수 없으면 실패합니다. 로컬에서 `--build-cache`를 쓸 때는 Docker를 켜고 돌립니다.
- 응답 시간 상한을 검사하는 테스트는 여유를 둡니다. 함께 도는 다른 서비스의 테스트 때문에 느려질 수 있습니다. 서비스끼리 같은 파일이나 고정 포트를 함께 쓰는 테스트도 만들지 않습니다.
- 캐시된 결과가 의심되거나 캐시 오류(예: `Could not load from local cache`)로 실패하면, Actions → Management → **Caches**에서 Branch를 `dev`로 골라 **`dev` 캐시를 모두** 지우고(쓰기 권한 필요, `gh cache delete --all --ref refs/heads/dev`로도 가능) `dev`의 최근 CI 실행을 다시 실행합니다. 하나만 지우면 그다음 최근 `dev` 캐시를 복원합니다. 의존성 캐시도 함께 지워져 다음 한 번은 느립니다.

### 실행 환경과 보안

- GitHub가 제공하는 Ubuntu 24.04 실행기를 씁니다. 실행마다 새 가상 머신이라 이전 실행이 남긴 것이 없고(아래 Gradle 캐시만 복원), 공개 저장소의 표준 실행기는 비용이 들지 않습니다. 자체 실행기는 외부 PR의 코드가 기계에 남을 수 있어 쓰지 않습니다.
- CI는 저장소 읽기 권한만 가지며 비밀값과 AWS 권한을 쓰지 않습니다. 외부 저장소에서 온 PR도 같은 조건으로 돕니다. 대상 저장소의 쓰기 권한·비밀값으로 실행되는 `pull_request_target`은 쓰지 않습니다.
- 액션은 태그가 아니라 커밋 SHA로 고정하고, 주석에 릴리스 태그를 적습니다. 태그는 옮겨질 수 있어 검토한 코드와 실행되는 코드가 달라질 수 있기 때문입니다(GitHub 보안 권고). 나온 지 2주가 지난 릴리스를 씁니다.
- 체크아웃한 저장소에 GitHub 토큰을 남기지 않습니다(`persist-credentials: false`).
- Gradle 캐시는 기본 브랜치(`dev`)의 실행에서만 저장하고 PR·main 실행에서는 읽기만 합니다. 기본 브랜치에 저장한 캐시는 모든 브랜치의 실행이 읽을 수 있고, 다른 브랜치에 저장한 캐시는 그 브랜치(와 그 브랜치를 대상으로 한 PR)에서만 읽을 수 있는 GitHub 캐시 규칙에 맞춘 `setup-gradle` 기본 동작입니다. 빌드 캐시도 같은 규칙이라, PR은 `dev`·main이 쓰는 캐시를 바꿀 수 없습니다. Gradle wrapper 파일이 공식 배포본인지도 함께 검사합니다.

### 액션 버전 올리기

액션을 올릴 때는 SHA와 주석의 태그를 함께 바꿉니다. SHA는 그 액션 저장소의 릴리스 태그가 가리키는 커밋인지 확인합니다.

```
curl -s https://api.github.com/repos/<소유자>/<저장소>/git/ref/tags/<태그>
```

결과의 `object.type`이 `tag`이면 그 `object.url`을 한 번 더 조회해 커밋 SHA를 얻습니다.

### 머지 조건

`dev`·`main`은 GitHub의 `Require CI` 규칙으로 PR과 `Gradle build`, `Terraform`, `Python 3.9`, `Python 3.15`의 성공을 요구합니다. 검사 출처는 GitHub Actions로 지정합니다. `main`은 기존 `Protect main` 규칙에 따라 승인 1명도 필요합니다.

최신 브랜치 반영 강제(`Require branches to be up to date before merging`)는 꺼두어, 다른 PR이 먼저 머지됐다는 이유만으로 최신화와 CI 재실행을 강제하지 않습니다. dev 반영 후 CI가 실패하면 원인을 해결한 뒤 main에 반영합니다. `Image and monitoring`은 관련 파일이 바뀐 PR에서만 돌기 때문에 필수 검사로 지정하지 않습니다.

## CD(운영 배포)

`main`에 머지되면 `deploy.yml`이 돌아 바뀐 서비스만 운영 ECS에 배포합니다. 결과는 Actions의 **CD** 실행 화면과 요약(배포 대상과 이유)에서 봅니다.

실패하면 GitHub가 그 실행을 일으킨 사람(main에 머지한 사람, **Run workflow**를 누른 사람)에게 알립니다. 메일로 받으려면 GitHub **Settings → Notifications**의 **System → Actions**에서 **Email**과 **Only notify for failed workflows**를 고르고 저장합니다.

| 단계 | 하는 일 |
|---|---|
| CI | 머지된 커밋으로 `ci.yml`의 검사를 수행합니다. Gradle은 `dev` 캐시에 입력이 같은 컴파일·테스트 결과가 있으면 재사용하고, 캐시가 없거나 입력이 바뀐 작업은 실행합니다. 실패하면 배포하지 않습니다 |
| Plan | 서비스마다 지금 실행 중인 이미지가 어느 커밋으로 만들어졌는지(ECR의 커밋 태그) 확인하고, 그 뒤로 이미지 내용이 바뀐 서비스만 고릅니다. 이전 배포가 끝나지 않았거나 실패한 서비스도 고릅니다 |
| Build | 고른 서비스의 이미지를 동시에 만들어 커밋 태그(SHA 앞 12자리)로 ECR에 올립니다. 같은 태그가 이미 있으면 다시 만들지 않습니다 |
| Deploy | 정해진 순서로 한 서비스씩, 최신 Task 정의에서 이미지만 바꾼 리비전을 등록하고 롤링 배포가 끝날 때까지 기다립니다. 최신 리비전이 이미 그 이미지면 다시 등록하지 않고, Service가 이미 그 리비전이면 다시 배포하지 않습니다(서비스를 지정한 수동 실행은 새 Task로 다시 띄움). 다른 배포(서킷 브레이커의 되돌리기 포함)가 진행 중이면 끝난 뒤 바꿉니다 |

### 배포 대상

이미지에 들어가는 파일이 바뀐 서비스만 배포합니다. 이미지 빌드는 `.dockerignore`가 보내는 파일만 씁니다.

- 그 서비스 폴더의 코드·설정(`src/test`, `load-test` 제외)
- `common/`: Eureka를 뺀 7개 서비스
- 루트 `build.gradle`·`settings.gradle`·`gradle/`·`gradlew`, `deploy/docker/`의 Dockerfile·시작 스크립트, `.dockerignore`: 8개 모두

문서·테스트·인프라 코드만 바뀐 머지는 배포하지 않습니다. 실행 중인 이미지와 비교하므로, 배포가 실패했거나 대기하던 실행이 더 새 실행으로 바뀌어 건너뛴 커밋의 변경도 다음 배포에 들어갑니다. 실행 중인 이미지는 끝난 배포에서 읽습니다. Service의 Task 정의는 갱신하는 즉시 새 리비전을 가리켜서, 끝나지 않은 배포를 이미 배포된 것으로 보지 않기 위해서입니다.

### 배포 순서와 이유

eureka → mock-bank → ledger → user → wallet → payment → exchange → gateway 순서로 하나씩 배포합니다.

- 다른 서비스가 호출하는 서비스를 먼저 배포합니다. Wallet은 Ledger·Mock Bank·User를, Payment는 Ledger·User·Wallet을, Exchange는 Ledger·Wallet을 호출하고, Gateway는 User·Wallet·Payment·Exchange로 요청을 넘깁니다. 새 API를 쓰는 코드가 그 API보다 먼저 배포되지 않게 하기 위해서입니다.
- 동시에 배포하지 않는 이유: 순서가 의미를 가지려면 앞 서비스의 배포가 끝나야 합니다. 또 롤링 중에는 새 Task를 이전 Task와 함께 띄우므로, 8개를 한꺼번에 하면 메모리가 약 8.4GB 더 필요해 앱 호스트 2대에 남는 메모리(2026-11-12 측정 약 5GB)를 넘습니다. 하나씩 하면 더 필요한 메모리는 최대 1.5GB입니다.
- 한 서비스가 실패하면 뒤의 서비스는 배포하지 않습니다. 서킷 브레이커가 실패를 판정하면 ECS가 완료된 이전 배포로 되돌립니다. 20분 안에 끝나지 않으면 CD만 멈추고 ECS의 배포는 계속됩니다. 다음 실행은 끝나지 않았거나 실패한 서비스를 다시 대상으로 잡아, 진행 중인 배포가 끝나기를 기다린 뒤 배포합니다. 원인을 고쳐 머지하면 남은 서비스까지 함께 배포됩니다.

### 롤링 배포 중 동작

- 서비스마다 정상 Task 1개를 유지한 채 새 Task를 띄우고, 새 Task가 정상(헬스 체크·Gateway는 ALB 상태 확인)이 된 뒤 이전 Task를 내립니다.
- Eureka에 등록하는 6개 서비스(eureka-server·mock-bank 제외)는 내려갈 때 Eureka에 `OUT_OF_SERVICE`를 알리고 20초 기다린 뒤 종료합니다. 처리 중인 요청이 끝나고 다른 서비스가 주소 목록을 갱신할 시간입니다.
- 이전 Task와 새 Task가 잠깐 함께 돕니다. Payment·Wallet·Exchange의 스케줄러는 두 Task에서 함께 돌아도 안전하다고 각 담당자가 확인했습니다(조건부 갱신, `SKIP LOCKED`, 유일 인덱스).
- 2026-11-13 초기 운영 시험에서 wallet·gateway·payment를 다시 배포하는 동안 0.5초마다 보낸 요청이 모두 성공했습니다. 당시 Eureka는 heartbeat 30초 설정에서 약 26초 동안 일부 요청이 503이었습니다. 이후 heartbeat를 5초로 줄이고 중복 LoadBalancer 캐시를 껐습니다. 한 조건의 로컬 재현에서는 목록 공백이 약 25초에서 약 5초로 줄었지만, 추가 시험에서 조회 시점이 달라지면 약 10초도 관측했습니다. 운영 반영 후 Eureka 교체 중 읽기 전용 약관 조회 339건은 모두 200이었습니다. 여러 업무 API를 포함한 초기 시험과 조건이 같지 않으므로 전체 API의 무중단을 보장하는 결과는 아닙니다. 주기별 비교와 선택 근거는 AWS 가이드의 "heartbeat 5초 선택 근거"에 있습니다.

### 팀원이 지킬 규칙

배포 순서로 막을 수 없는 변경은 한 번의 배포 안에서 이전 버전과 새 버전이 함께 동작하게 나눠야 합니다.

- **API 제거·변경:** 새 API(또는 필드)를 먼저 추가해 배포하고, 호출하는 쪽이 모두 새 API로 바꾼 뒤 다음 배포에서 이전 것을 지웁니다.
- **DB(Flyway):** 컬럼·테이블 추가처럼 이전 코드가 계속 동작하는 변경만 먼저 하고, 삭제·이름 변경은 이전 코드가 더 이상 쓰지 않게 된 뒤의 배포에서 합니다. 롤링 중에는 이전 Task가 새 스키마로 돕니다.
- **Enum·메시지 형식:** 새 값을 받는 쪽을 먼저 배포한 뒤 보내는 쪽에서 쓰기 시작합니다.
- **eureka가 다시 배포되는 머지:** `eureka-server/`(테스트·부하 시험 제외), 루트 `build.gradle`·`settings.gradle`·`gradlew`·`gradle/`, `deploy/docker/`의 Dockerfile·시작 스크립트, `.dockerignore`가 바뀌면 eureka도 다시 배포되어 목록 복원 중 일부 요청이 503일 수 있습니다(위 "롤링 배포 중 동작"). 이런 머지는 사용자가 없는 시간에 합니다. `services`에 `eureka`를 넣는 수동 실행도 같습니다.

### 다시 배포하기

Actions의 **CD** → **Run workflow**에서 브랜치를 `main`으로 고르고 실행합니다(production 환경이 main 외의 실행을 막습니다).

- 입력을 비우면 바뀐 서비스와, 이전 배포가 끝나지 않았거나 실패한 서비스를 배포합니다. 실패한 배포를 원인 해결 뒤 다시 할 때 씁니다.
- `services`에 서비스 키(`eureka`, `mock_bank`, `ledger`, `user`, `wallet`, `payment`, `exchange`, `gateway`)를 쉼표로 넣으면 바뀌지 않았어도 새 Task로 다시 띄웁니다. Terraform이 바꾼 Task 설정(환경 변수 등)을 반영하거나, SSM 비밀값을 바꾼 뒤 새 값을 읽게 할 때 씁니다. 비밀값은 Task가 시작할 때 주입되므로 실행 중인 Task에는 반영되지 않습니다(AWS ECS 문서). 2026-11-13 payment로 확인했을 때 같은 리비전으로 새 Task가 교체됐고 그동안 요청 오류는 없었습니다.
- 배포는 한 번에 하나만 돌고, 기다리는 실행은 하나만 남습니다. 수동 실행이 기다리는 동안 main에 새 머지가 오면 수동 실행은 취소되고 새 실행으로 바뀝니다. 바뀐 서비스는 새 실행이 배포하지만, `services`로 지정한 서비스는 빠지므로 다시 실행합니다.
- 실행 기록의 **Re-run**은 원래 실행의 커밋으로 다시 돕니다. 가장 최근 실행이 실패했을 때(예: AWS 설정을 고친 뒤)에만 씁니다. 실패한 작업만 다시 실행해도 이미 배포를 마친 서비스는 다시 배포하지 않습니다. 단, `services`를 지정한 수동 실행이 실패했다면 Re-run 대신 실패한 서비스만 지정해 **Run workflow**로 다시 실행합니다. Re-run은 이미 다시 띄운 서비스도 또 띄울 수 있습니다. 더 새 커밋이 이미 배포된 뒤 이전 실행을 다시 실행하면, 운영을 이전 이미지로 되돌리지 않도록 배포 대상 선택과 배포 단계에서 멈춥니다.

### 되돌리기(롤백)

- **새 버전이 기동하지 못하거나 헬스 체크에 실패하면** ECS 서킷 브레이커가 완료된 이전 배포로 자동으로 되돌립니다. CD 실행은 실패로 끝나고, 원인을 고쳐 머지하면 다시 배포합니다. 2026-11-13 시작하자마자 종료하는 버전으로 시험했을 때 약 8분 뒤 실패를 판정했고(ECS가 실패한 Task의 재시도 간격을 늘림), 그동안 이전 Task가 계속 응답했으며 CD의 감시는 서킷 브레이커 실패로 멈췄습니다.
- **배포는 됐지만 기능에 문제가 있으면** 문제 PR을 main에서 되돌리는(revert) PR을 머지합니다. CD가 CI를 거쳐 바뀐 서비스만 이전 코드로 다시 배포합니다(첫 자동 배포 기준 약 20분). 되돌린 기록이 Git에 남고 main과 운영이 어긋나지 않습니다.
- AWS에서 이전 Task 정의 리비전을 직접 지정해 되돌리지 않습니다. main과 운영이 달라져, 다음 머지 때 CD가 그 서비스를 다시 대상으로 잡아 문제 버전을 배포합니다.
- 비상 작업이나 시험으로 AWS CLI에서 설정을 바꾼 리비전을 등록했다면 끝난 뒤 등록 해제합니다. CD는 패밀리의 최신 리비전에서 이미지만 바꿔 등록하므로, 남겨 두면 다음 배포가 그 설정을 이어받습니다. CD 배포가 실패해 생긴 리비전은 이미지만 다르므로 정리하지 않아도 됩니다.
- **DB 마이그레이션 파일은 되돌리지 않습니다.** 운영에 이미 적용된 Flyway 마이그레이션 파일을 revert로 지우면, 가장 최근 것은 무시되고(Flyway 기본값 `*:future`) 스키마는 바뀐 채 남으며, 그보다 이전 것을 지우면 시작할 때 검증에 실패해 서비스가 뜨지 않을 수 있습니다. 스키마를 되돌려야 하면 새 마이그레이션을 추가합니다. 그래서 스키마 변경은 이전 버전 코드도 동작하는 방식으로만 합니다(위 "팀원이 지킬 규칙").

### 보안

- AWS를 쓰는 Plan·Build·Deploy 작업만 `production` 환경을 쓰고(CI 작업은 쓰지 않음), 이 환경은 `main`에서 시작한 실행만 허용합니다. AWS 권한은 GitHub OIDC로 받으며, AWS 역할은 이 저장소의 `production` 환경 토큰만 믿습니다. 저장된 AWS 키는 없습니다.
- 배포 역할이 할 수 있는 일은 8개 앱 ECR 저장소의 이미지 조회·푸시, 8개 Service의 조회·갱신, Task 정의 조회·등록과 앱 Task 역할 전달뿐입니다. privileged 컨테이너가 있는 Task 정의는 등록할 수 없습니다.
- 공개 저장소라 실행 로그를 누구나 볼 수 있습니다. 역할 ARN은 환경 비밀값으로 두고 AWS 계정 ID는 로그에서 가립니다.
